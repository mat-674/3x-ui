The **nginx perimeter** is a single-port arrangement: Xray owns **443/tcp** with a
VLESS + REALITY inbound, and every TLS client that does not authenticate is
handed to a real **nginx** on loopback. nginx terminates TLS with your real
certificate and answers with the decoy website, the panel on its secret base
path, and the subscription on its secret paths.

A probe therefore sees a genuine nginx handshake on 443, the real certificate for
the domain, and a real website behind it — because that is exactly what answers.

<Callout type="info">
  The panel **generates and owns** the whole nginx config — `edge/nginx.conf`
  inside the panel's database folder (`/etc/x-ui/edge/nginx.conf` on Linux), with
  its logs, pid file and temp directories beside it. It never reads, extends or
  edits `/etc/nginx`, so an unrelated system nginx cannot change what your
  perimeter serves. nginx itself must be installed on the host: set
  `edgeNginxBin` to its path, or leave it empty to run `nginx` from `PATH`.
</Callout>

## How a request is routed

```text
client ── TLS :443 ──►  Xray   VLESS + REALITY   (holds 443/tcp)
                          │
                          ├─ authenticated client ──► VLESS + XTLS-Vision ──► internet
                          │
                          └─ every other handshake
                               dest 127.0.0.1:8443, xver 1
                                        │
                                        ▼
                                  nginx (real certificate)
                                        │
              ┌─────────────────────────┼─────────────────────────┐
              ▼                         ▼                         ▼
        /              /<webBasePath>/                  /<subPath>/
   decoy website                              subscription  127.0.0.1:2096
   (uploaded site)      panel 127.0.0.1:2053
```

| Path                          | Served by         | Notes                                                                 |
| ----------------------------- | ----------------- | --------------------------------------------------------------------- |
| `/` and ordinary paths        | the decoy site    | `root` is the uploaded site; `index` is its entry file.                |
| `/<webBasePath>/…`            | the panel         | `location <webBasePath>`, proxied to `127.0.0.1:<webPort>`.           |
| `/<subPath>/`, `/<json>/`, `/<clash>/` | the subscription | Only emitted while the subscription server is enabled.        |
| anything else                 | the site's 404    | `error_page 404 /404.html`, served from the site's own `404.html`.    |

The catch-all is `try_files $uri $uri/ =404`, so only **404** is remapped to the
site's own `404.html`. A request that resolves to a directory with no `index` file
still answers nginx's 403 — the generated config remaps 404 only.

Both proxied locations get `X-Forwarded-Proto https`, and nginx **overwrites**
`X-Forwarded-For` and `X-Real-IP` with the client address instead of appending to
whatever the client sent. The panel location additionally carries the WebSocket
upgrade headers and a one-hour read timeout.

## Why a real nginx behind REALITY

- **The handshake is nginx's.** Xray forwards the raw bytes of a non-client
  connection to `dest`, so the ClientHello is answered by nginx's own TLS stack,
  with nginx's ALPN choice (`h2` or `http/1.1`) and nginx's cipher selection.
  There is no re-implemented TLS server to fingerprint.
- **The certificate is the real one.** nginx presents `edgeCertFile` /
  `edgeKeyFile`, so a scanner validating the chain gets a normal Let's Encrypt
  certificate for your domain — not a self-signed placeholder.
- **Vision still works.** Authenticated clients never reach nginx: REALITY
  terminates their connection and `xtls-rprx-vision` runs on the Xray side. The
  decoy path and the proxy path share a port, not a TLS stack.
- **Nothing else answers on the public port.** The panel itself listens on
  loopback only, so the only TLS implementation the internet can talk to is
  nginx, configured with `server_tokens off` (no version banner), no directory
  listing, and a 404 remapped to the site's own page.

### Why not a TLS front inside the panel

An earlier design terminated TLS in the panel itself with a Go server. It was
removed: a second TLS implementation facing the internet has its own fingerprint,
its own ALPN and session-resumption behaviour, and its own certificate store, and
every part of it has to be kept indistinguishable from nginx by hand. Delegating
to nginx makes that indistinguishability structural instead of a maintenance
burden.

### Why not Hysteria2 / QUIC for the perimeter

Hysteria2 was considered for the whole perimeter and rejected, for two reasons
that both come down to the handshake not being nginx's:

- **The TLS stack is a Go QUIC stack, not nginx.** Hysteria2's server is an
  HTTP/3 server built on `quic-go` (`transport/internet/hysteria` imports
  `apernet/quic-go` and `apernet/quic-go/http3`). Its transport parameters and
  HTTP/3 behaviour are that library's, and there is no way to make them
  byte-identical to nginx's HTTP/3 — so a probe that speaks QUIC can tell it is
  not talking to nginx.
- **The default masquerade is not a website.** With `masquerade.type` unset the
  server falls back to Go's `http.NotFoundHandler`, which answers a bare
  `404 page not found`. That response is itself a fingerprint, and it is the
  opposite of what a decoy site is for.

TCP + REALITY + nginx has neither problem: the fallback connection is handed to
nginx as bytes, so the TLS session a visitor completes is nginx's own.

## Settings

All of these live in **Settings → Nginx perimeter**; the JSON names below are the
setting keys (the same names the REST API uses).

| JSON name             | Default        | Meaning                                                                                         |
| --------------------- | -------------- | ----------------------------------------------------------------------------------------------- |
| `edgeEnable`          | `false`        | Run the perimeter. Also moves the panel's own listener to loopback.                              |
| `edgeListen`          | `127.0.0.1`    | Address nginx binds. Keep it on loopback: it is reachable only through REALITY.                  |
| `edgePort`            | `8443`         | Loopback port nginx binds, and the port the REALITY inbound's `dest` points at.                  |
| `edgeServerNames`     | _(empty)_      | Names nginx answers for, comma- or space-separated. Empty uses the certificate's own DNS names.   |
| `edgeCertFile`        | _(empty)_      | PEM the perimeter presents. Empty reuses the panel's `webCertFile`.                               |
| `edgeKeyFile`         | _(empty)_      | Private key. Empty reuses the panel's `webKeyFile`.                                              |
| `edgeNginxBin`        | _(empty)_      | Path to the nginx executable. Empty runs `nginx` from `PATH`.                                     |
| `edgeProxyProtocol`   | `true`         | Expect a PROXY protocol header from Xray. Must match the REALITY inbound's `xver` — see below.     |
| `edgeHTTPPort`        | `0`            | Plaintext port served alongside TLS: ACME validation plus a redirect to HTTPS. `0` leaves it off. |

Related settings the generated config reads:

| JSON name                                  | Default   | Role in the perimeter                                                    |
| ------------------------------------------ | --------- | ------------------------------------------------------------------------ |
| `webBasePath`                              | `/`       | The panel's `location` prefix. **Set a real secret path** — see below.    |
| `webPort`                                  | `2053`    | Panel upstream: `127.0.0.1:<webPort>`.                                    |
| `frontSiteId`                              | `0`       | Which uploaded site is served at `/`; `0` means the built-in placeholder. |
| `subEnable`                                | `true`    | When off, no subscription locations are emitted at all.                   |
| `subPort`                                  | `2096`    | Subscription upstream.                                                    |
| `subPath` / `subJsonPath` / `subClashPath`  | `/sub/`, `/json/`, `/clash/` | The three subscription prefixes.                      |

Every perimeter value is re-read on each Apply, so a saved change reaches nginx
without editing a file. Two things are still decided at panel start: whether the
panel itself binds loopback, and whether the perimeter is applied at boot.

<Callout type="warn">
  The base path must not stay at `/`. The panel's location is emitted as
  `location <webBasePath>`, so a root base path produces **two** `location /`
  blocks — the panel proxy and the site's catch-all — which nginx rejects as a
  duplicate location; Apply then reports nginx's message and the running
  perimeter stays untouched. Set a long random path in
  [Panel Settings](/docs/config/panel) first; the panel already warns about the
  default one.
</Callout>

## The `xver` rule

`edgeProxyProtocol` and the REALITY inbound's `xver` are two halves of one
agreement. When the setting is on, the generated config binds
`listen … ssl http2 proxy_protocol` and adds:

```text title="generated nginx config (excerpt)"
set_real_ip_from 127.0.0.1;
set_real_ip_from ::1;
real_ip_header proxy_protocol;
```

The matching REALITY inbound must have `xver` set to **1** (or `2`), so Xray
prepends a PROXY protocol header before it hands the connection to nginx. `xver`
is part of the REALITY inbound's `realitySettings`, next to `dest` — `1` sends the
text (v1) header, `2` the binary (v2) one, and nginx accepts both when its listen
line carries `proxy_protocol`:

```json title="REALITY inbound (excerpt)"
"realitySettings": {
  "dest": "127.0.0.1:8443",
  "xver": 1,
  "serverNames": ["panel.example"],
  "privateKey": "<x25519 private key>",
  "shortIds": ["<hex short id>"]
}
```

If the two disagree, the decoy site simply breaks:

| `edgeProxyProtocol` | inbound `xver` | What happens                                                                       |
| ------------------- | -------------- | ---------------------------------------------------------------------------------- |
| on  (`true`)        | `0`            | nginx waits for a PROXY header that never arrives and drops the connection.        |
| on  (`true`)        | `1`            | Correct.                                                                            |
| off (`false`)       | `1`            | nginx reads the PROXY line as TLS and the handshake fails.                          |
| off (`false`)       | `0`            | Correct, but the panel loses the real client address (next section).                |

### Real client IPs

With `real_ip_header proxy_protocol` and `set_real_ip_from` limited to loopback,
`$remote_addr` inside nginx is the **visitor's** address, not `127.0.0.1`. That
matters because nginx forwards `$remote_addr` as `X-Real-IP` / `X-Forwarded-For`
and the panel trusts loopback by default (`trustedProxyCIDRs`
`127.0.0.1/32,::1/128`), so the panel's own IP resolution — the login limiter,
request logging, WebSocket logs — sees the real client.

Without it every request reaches the panel from `127.0.0.1`. The login limiter
keys its buckets on IP, so all operators and all attackers share one bucket: 5
failed attempts for one username block that username for 15 minutes, and 25
failed attempts from anywhere block **every** login from everywhere for 15
minutes — including yours.

<Callout type="info">
  Fail2ban is not affected by this. Its `3x-ipl` jail is fed by the per-client
  source addresses Xray reports for proxy connections, not by nginx request
  headers, so it already sees real addresses whether or not `xver` is set.
</Callout>

## Certificates

The perimeter reuses the panel's certificate whenever it can, so there is one
file to renew:

1. `edgeCertFile` / `edgeKeyFile` when both are set;
2. otherwise `webCertFile` / `webKeyFile` (the panel's own pair);
3. server names come from `edgeServerNames`, else from the certificate's DNS
   names; with neither, Apply is refused outright rather than generating a config
   that cannot match a name.

Renewal is a **file replacement** at the same path — nginx keeps the old
certificate in memory until it is reloaded, and Apply validates the new
configuration with `nginx -t` and then issues `nginx -s reload`.

`x-ui` menu **`20 — SSL Certificate Management`** registers the renewal hook for
you: `acme.sh --installcert` is called with `--reloadcmd` (default
`x-ui restart`, and the menu offers the `systemctl reload nginx ; x-ui restart`
preset). A panel restart re-applies the perimeter on startup, which reloads the
generated nginx with the renewed files. Note that `systemctl reload nginx` in
that preset addresses a *system* nginx; the generated perimeter is reloaded by
the panel itself.

<Callout type="warn">
  With only **443** open, neither HTTP-based challenge works: HTTP-01 needs a
  reachable HTTP port (the `x-ui` menu validates on the panel's web port), and
  TLS-ALPN-01 needs to hold 443 itself, which Xray already does. Use **DNS-01** —
  `x-ui` menu **`21 — Cloudflare SSL Certificate`**, or any other ACME client
  with a DNS challenge. See [SSL certificates](/docs/config/ssl-certificates).
</Callout>

### Serving port 80

The simplest way out of that corner is to let the perimeter own port 80. Set
`edgeHTTPPort` to `80` and the generated config gains a second server block that
answers ACME challenges from `<state dir>/acme` and redirects everything else to
HTTPS. Renewal then runs as a plain webroot request and no firewall rule has to
be touched again:

```bash
~/.acme.sh/acme.sh --issue -d site.example --webroot /etc/x-ui/edge/acme
```

This also looks more like a real site: an HTTPS server whose port 80 stays silent
is a mild signal of its own, while a redirect is what ordinary hosting does. The
block carries `server_tokens off` and serves nothing but the challenge directory,
so it adds no surface — and never proxies the panel or the subscription.

Apply refuses the config when the port is already taken by something else, naming
the port, rather than letting nginx fail to start and take the whole perimeter
down. Set `edgeHTTPPort` back to `0` to drop the block again.

<Callout type="info">
  Plain TLS traffic on port 80 cannot carry REALITY: the fallback is the whole
  point of 443, and Xray's REALITY listener needs a TLS handshake to proxy. What
  port 80 can carry is HTTP — the challenge and the redirect above.
</Callout>

## Set it up

<Steps>

<Step>
### Get a certificate for the domain

Use the [`x-ui` SSL menu](/docs/config/ssl-certificates) (menu `20`, or `21` for
the Cloudflare DNS-01 wildcard) or your own ACME client. The files must cover the
domain clients will use as the REALITY server name.
</Step>

<Step>
### Upload the decoy site

In **Settings → TLS Front**, upload a `.zip` of the site to serve at `/`. Its
`index.html` must be at the archive root (or be the only `.html` file); one
wrapping top-level folder is stripped automatically. Select the site — that sets
`frontSiteId`. With no site selected the perimeter serves a neutral placeholder
page, so a probe never reaches an empty root.

The archive is capped at 128 MiB compressed with a 128 MiB uncompressed budget,
5000 entries, and 16 levels of nesting; a rejected archive leaves nothing behind.
</Step>

<Step>
### Configure the perimeter

In **Settings → Nginx perimeter**: enable it, keep `edgeListen` on `127.0.0.1`,
keep `edgePort` at `8443` unless you have a reason, list the domain in
`edgeServerNames`, leave both certificate fields **empty** to reuse the panel's
pair, and leave PROXY protocol **on**.
</Step>

<Step>
### Save, then Apply

**Save** stores the settings; **Apply** writes the generated config, runs
`nginx -t`, and starts or reloads nginx with it. Use **Show generated config** to
see exactly the text nginx is given — that is also the fastest way to check the
server names, certificate paths and subscription prefixes the panel resolved.
</Step>

<Step>
### Restart the panel

The panel decides at startup whether its own listener binds loopback, so restart
it (the **Restart panel** button on the Settings page, or `x-ui restart`) —
otherwise it keeps listening on the public port directly. Verify that
`https://<domain>/<webBasePath>/` still answers afterwards.
</Step>

<Step>
### Create the 443 REALITY inbound

Create a **VLESS** inbound on port **443**, security **REALITY**, flow
`xtls-rprx-vision`, and:

- **Dest**: `127.0.0.1:8443` (your `edgeListen`:`edgePort`);
- **Server names / SNI**: the same domain;
- **`xver`**: `1` when `edgeProxyProtocol` is on, `0` when it is off.

See [REALITY](/docs/config/reality) for keys, short IDs and the flow.
</Step>

</Steps>

## Check that it works

```bash title="the decoy site"
curl -sk https://panel.example/ | head -n 5
# the uploaded site's HTML (or the placeholder page)
```

```bash title="the panel on its secret path"
curl -sk -o /dev/null -w '%{http_code} %{http_version}\n' https://panel.example/adm9x/
# 200 2   (the panel's login page, negotiated over HTTP/2)
```

```bash title="the certificate and ALPN"
openssl s_client -connect panel.example:443 -servername panel.example -alpn h2 </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
# subject=CN = panel.example — the real certificate, presented by nginx
# because this handshake was not an authenticated REALITY client
```

In the full `openssl s_client` output, expect `ALPN protocol: h2` (nginx
advertises `h2` because the listener is `ssl http2`, and the client asked for it)
and `Verify return code: 0 (ok)` — the latter needs a complete chain in
`edgeCertFile`, i.e. `fullchain.pem` rather than the leaf alone. A path the site
does not define returns the site's own 404 page, not an nginx error page. The
subscription is reachable at `https://<domain>/<subPath>/` when the subscription
server is enabled.

## Operational consequences

- **The panel listener moves to loopback.** With the perimeter enabled the panel
  binds `127.0.0.1:<webPort>` and speaks plain HTTP, because nginx has already
  terminated TLS. Session cookies are marked secure unconditionally, and HSTS is
  sent whenever the perimeter is on (or the panel has a usable certificate of its
  own) unless `XUI_SKIP_HSTS` is set.
- **Do not publish `webPort` or `edgePort`.** The panel port must stay closed —
  publishing it puts the panel outside the decoy entirely — and the perimeter
  port is loopback-only by design. Open **443/tcp** and your SSH port, nothing
  else; see [Ports & firewall](/docs/reference/ports-firewall).
- **The perimeter is on the critical path for every client, not just visitors.**
  REALITY dials `dest` as the first thing it does with an incoming connection, so
  if nginx is not listening, connections fail before authentication even runs.
  That is why the panel applies the perimeter *before* starting Xray at boot.
  Stopping the panel stops nginx too.
- **A bad config never replaces a good one.** Apply writes the config, runs
  `nginx -t`, and only then starts or reloads; a rejected config leaves the
  running process alone and reports nginx's message.
- **Status is read-only.** **Perimeter status** shows whether the config is
  valid, whether something answers on the listen address (a TCP dial, not a pid
  check), the resolved server names, the panel upstream, how many subscription
  paths are routed, and the certificate names and expiry. The same data is at
  [`GET /panel/api/edge/status`](/docs/reference/api/nginx-perimeter), with
  `apply`, `stop` and a config preview alongside it.

## What it does not do

- **No HTTP/3.** The listener is `ssl http2` and never advertises `h3` in ALPN,
  so there is no QUIC surface on 443/tcp at all.
- **No multi-site hosting.** One `server` block, one decoy site. It is not a
  general web server for several domains.
- **No WAF, no rate limiting, no caching.** The generated config has no such
  modules; the panel's own login limiter and Fail2ban remain the rate-limiting
  and banning layers.
- **No CDN.** Putting a CDN in front would terminate TLS at the CDN, which
  defeats the whole arrangement: the client-facing handshake must be this nginx.
